Self-healing support agent

Lexsi hackathon, Track 3, problem statement 8. Updated 2026-11-10, grounded in the actual AgentTune and AuditKIT source (not just their docs). Status: round 1 has actually run - a real baseline against tau2-bench retail, real failures found and classified (AgentTune's FailureDetector/FailureClassifier, src/shipwright/heal/agenttune_bridge.py), 35 tool-description patches applied through the ledger, and teacher-generated SFT data built for the weight-fix path. No local fallback for AgentTune: it installs --no-deps on Linux (CI, Cloud Run Jobs, HF Jobs), not on a CPU-only macOS dev machine (AGENTS.md known traps). A real LoRA training run and a real gate decision still need GPU time and the Vertex AI budget, see docs/pipeline/training.md and docs/pipeline/gate.md.

Service boundaries

Three processes: two that do the work, below, and one read-only process that replays what they did for a person to watch, covered in the next section. None of them is a 24/7 daemon.

ServiceOwnsWhy separate
agent-runtime Runs the tau2-bench tasks for one round against the currently-deployed Tiny Aya Global + LoRA adapter (scripts/baseline.py, via Cloud Run Jobs - docs/setup/cloud-runs.md). Writes traces.jsonl (every turn's raw output, not only the parsed tool call) plus otel_spans.jsonl built from it. Stateless beyond the adapter checkpoint it loads. Never needs a teacher-model key, AuditKIT, or write access to the tool ledger. The thing that stands in for "serving a customer" should not be able to retrain itself or spend API budget on its own.
self-heal control plane Run once a round's traces.jsonl exists, not continuously: scripts/classify.py (AgentTune's FailureDetector + FailureClassifier, src/shipwright/heal/agenttune_bridge.py, plus our rule labels), scripts/tool_fix.py (the tool-patch ledger), scripts/round_status.py (AgentTune's RetrainingTrigger), scripts/train_lora.py (HF Jobs), and scripts/gate_eval.py (AgentTune's DeploymentGate + AuditKIT thresholds). Separate scripts, not one long-running process, each independently re-runnable. Everything expensive or risky (teacher API calls, retraining, redeploy decisions) lives in steps that are easy to kill, re-run, or roll back without touching the runtime.

AgentTune also ships FullClosedLoop, a true online/always-on variant (run_forever(), a background retrain thread so the event buffer keeps filling during retrain). We use the same underlying classes but drive them once per round instead of as a daemon: the task pool is frozen and finite, and a 24/7 GPU process is the wrong trade against a GCP budget that auto-kills billing at Rs 3000/month. This is a cost decision, not a capability gap.

Demo: the loop, round by round

control-room (src/shipwright/control_room/app.py), read-only with respect to everything above. It never calls a teacher API, a trainer, or the gate itself - it only reads the run-dir files the harness scripts already produce (traces.jsonl, failures.jsonl, patches/ledger.jsonl, round_status.json, gate_decision.json) and renders them step by step. This exists because a static before/after comparison (one input, two model outputs side by side) is the right demo for a team that trained one hardened model once, but it hides the one thing that makes a self-healing system worth building: that it is a loop, with a gate in the middle that is allowed to say no. The demo has to show the loop, not just its endpoint. Deploys as its own Hugging Face Space image, infra/space/.

Library integration map

Exact calls per stage, confirmed against the AgentTune and AuditKIT source (not just their docs) on 2026-11-09/10.

StageCallNote
RunAgentTune Project rollout/harness, our own sandbox_tools() Tool execution in a subprocess; a crashing or hung tool cannot take down the rollout. This sandbox is ours, not AgentTune's isolate_tools() - deliberately: it is generic timeout/fallback infrastructure, not self-healing domain logic, so writing our own does not carry the "library as fallback" risk a reimplementation of AgentTune's actual detect/classify/ generate/gate classes would (README.md, "Why no local fakes"). Tiny Aya has no hosted SDK with structured tool-calling the way Claude's Messages API does - Cohere-family tool use is prompt-level (a chat template renders the tools in, the model answers with a delimited action block inside its raw text). AgentTune's rollout/harness already parses that action-block format and already has chat-template repair logic for `CohereLabs/tiny-aya-fire`; the real runner calls into that rather than a hand-written parser. This is also why logging the full raw text matters so much here specifically: it is the only faithful record at all, not just extra context for the classifier.
ObserveOTel spans (GenAI semantic conventions) → AgentTune EventLog.to_audit_records() + our raw-text sidecar to_audit_records() emits one record per TOOL_CALL event only; it never reads TEXT/REASONING events. We log the raw model output ourselves or wrong-reasoning failures are unclassifiable. See AGENTS.md traces.
DetectFailureDetector.scan_audit_log() Rule-based only, byte-offset incremental: loop_collapse (stage repeated past max_revisits), tool_crash (tool-call status is error), low_judge_score (an upstream judge score under threshold — the detector does not judge, it reads a score already written to the log).
Classifysubclassed FailureClassifier Default ROOT_CAUSES is a class attribute (wrong_tool, wrong_routing, incomplete_reasoning, hallucinated_output, loop_collapse) and the default prompt truncates context to 2000 characters. We subclass to feed the full raw-text sidecar, since the default truncation can cut off exactly the reasoning text that explains a hallucinated_output failure.
Routeours Maps the 5 ROOT_CAUSES plus tool_crash onto tool fault / model fault / environment fault. Not an AgentTune or AuditKIT concept — this is the piece AGENTS.md calls out as ours to add.
Tool fixour patch ledger JSON diff (before/after tool spec), one-step rollback, re-verified by re-running the same failing tasks through our own sandbox before the patch is marked resolved.
Model fix (wrong_tool, loop_collapse)TrainingExampleGenerator AgentTune's generator calls a teacher model itself (litellm) and scores completions with TAC + TER. It only acts on these two root causes — everything else returns None.
Model fix (wrong_routing, incomplete_reasoning, hallucinated_output) our teacher-replay generator Same list[ClassifiedFailure] -> list[TrainingExample] contract as AgentTune's generator, so it plugs into the same SelfHealLoop unchanged. This exists because AgentTune's own generator has no coverage for 3 of our 5 model-fault labels, not because we are duplicating something it already does.
Curatescripts/build_sft.py's own dedup (first-wins on identical rendered conversations) CuratorKIT is optional per the hard rules and not currently used - see "CuratorKIT" below. If added later, it would run curate-only (generation_task=None) through a thin flatten/reconstruct adapter, since none of its exporters have a tool-call schema.
Traincreate_distill_trainer(student="CohereLabs/tiny-aya-global", use_peft=True, ...) TRL + PEFT backend, with chat-template repair logic already written for the Tiny Aya family. Replay mix (old passing runs + new corrections) is our own concatenation before this call; AgentTune does not mix datasets for you.
GateDeploymentGate.evaluate_decision() AND AuditKIT episode_from_openai_messages/reliability()/ak.compare AuditKIT has no deployment gate of its own — it produces RunResult / RunComparison scores. Our wrapper approves a candidate only if all of: AgentTune's own task-accuracy A/B regression check passes, with a floor well above its default of 1 (min_valid_runs, configs/gate.yaml); AuditKIT's reliability() pass^k / pass-hat-k does not regress, and only counts as reliable when independent=True (trials genuinely independent - the keyword is independent, not reset_confirmed, a mistake caught once already, AGENTS.md known traps); AuditKIT's RunComparison.grade() on BFCL v3 is not FAIL, via tau2 traces adapted to OpenAI-style messages (eval_metrics.trace_to_openai_messages) since AuditKIT ships a BFCL loader but no tau2-bench loader.
PromoteRunResult.push_to_hub() + HF Hub adapter tag Satisfies the public-artifacts rule directly from AuditKIT's own output.

Decisions, frozen 2026-11-09

  • No Kafka. The actual concurrency need is one embarrassingly parallel batch of tau2-bench tasks per round, not a multi-consumer streaming system. Confirmed by reading the source: AgentTune itself has zero pub/sub or event-bus concept anywhere — its own idiomatic pattern is a flat polled JSONL plus a driven loop. Building a broker around a library that assumes none exists would add infrastructure with no AgentTune touchpoint, under a budget that auto-kills billing at Rs 3000/month.
  • OpenTelemetry is the capture and viewer layer. No external viewer (Langfuse or otherwise) is wired in. traces.jsonl is the loop's own input; otel_spans.jsonl is built from it after each run for anyone who wants a GenAI-span view, OTLP export only when OTEL_EXPORTER_OTLP_ENDPOINT is set. See docs/ops/observability.md.
  • The gate is an AND of checks, never an OR, and missing data is a reject on every one of them. AgentTune's DeploymentGate alone (with its min-sample trap fixed) is necessary but not sufficient — it only checks task accuracy. AuditKIT's BFCL regression grade, pass^k reliability, and our own stricter valid-run accounting close the "did we break something else," "is this actually more reliable, not just luckier," and "do we even have enough real data to trust this" gaps.
  • CuratorKIT is optional and not currently used. The real pipeline's dedup (scripts/build_sft.py) and the gate's AuditKIT-backed thresholds already cover what a submission needs; CuratorKIT's curate-only mode (dedup, hallucination-gate, label balancing) would slot in as an extra pass on data already generated and already known to pass the task oracle, not a required step.
