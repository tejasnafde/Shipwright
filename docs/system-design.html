System design

Shipwright

A self-healing service for a tool-calling support agent. It runs the agent, finds the conversations it failed, classifies why, applies the remedy that fits the cause, and redeploys only when a frozen gate measures the new system as better on tasks it never trained on.

1. Overview

The agent is Tiny Aya Global (3.35B, Cohere Labs) with a LoRA adapter, serving retail customer support in tau2-bench: a simulated customer, a policy, sixteen tools over an order database, and a grader that checks the final database state rather than the wording of a reply.

Shipwright closes the loop around that agent. One command starts an unattended run in the cloud. Each round diagnoses the deployed system's failures, builds a candidate that addresses them, and puts the candidate through an eight-check gate against the deployed system. A candidate that passes is recorded in a promotion ledger and becomes the deployed system; one that fails is never served, and its failed checks choose the next round's remedy.

2. Goals and non-goals

Goals

  • Detect every failed conversation and attribute it to a cause, with the evidence kept.
  • Fix each cause at the cheapest layer that can fix it: the tool interface before the weights.
  • Never serve an unmeasured change: redeployment is gated on task accuracy on held-out tasks.
  • Run a whole round with no person in the loop, inside a declared spend cap, resumable after any failure.
  • Make every decision reproducible: configs, code sha, image digest, data revision and gate inputs are recorded.

Non-goals

  • Online learning from live customers: rounds are batch, on benchmark tasks.
  • A general agent framework: the harness is specific to tau2-bench and prompted tool calls.
  • Replacing a frontier model: the teacher is stronger; the goal is a small model that is cheaper to serve and improves itself measurably.

3. Architecture

Three planes. The control plane is one Cloud Run execution running the loop controller. The work plane is where stages execute: CPU stages in the same execution, GPU stages as HF Jobs. The record plane holds everything durable: run directories in Cloud Storage and on the Hub, the promotion ledger, adapters and datasets.

4. Lifecycle of a round

The controller (loop/controller.py) is pure: it decides the order of stages, the caps, retries, when to stop and what the next round is, and takes the stage functions as hooks, so every path is unit-tested with fakes. The recipe (loop/recipe.py) maps the last gate's failed checks to a remedy.

A run ends in one of five statuses: promoted, rejected (no promotion in the rounds asked for), stopped (a stage failed twice; the same command resumes), over_budget, exhausted.

5. Decision points

Four decisions, each owned by one module and each recorded with its inputs:

DecisionOwnerInputsOutput
Which remedy fits a failureheal/classify.py (router)rule labels, AgentTune root cause, optional judgetool_fix, weight_fix or no_fix per failure

Whether a candidate shipsheal/gate.py + AgentTune DeploymentGateboth systems on 20 held-out tasks x 3, BFCLpromote or reject, every check with its numbers
TOOL FAULT → tool_fix

The interface misled the model: copied example ids, context lost to the harness. Fixed by description patches (ledger, one-step rollback) and tool guards. No GPU.

MODEL FAULT → weight_fix

The model reasoned or acted wrongly: invented ids, wrong tool, skipped policy step, premature transfer. Fixed with teacher data and a LoRA round.

ENVIRONMENT → no_fix

Infra errors and simulator faults. Retried by the harness, never used as training data.

7. The serving harness

Tiny Aya has no native tool calling and an 8,192-token window. The harness adapts tau2-bench to it at the litellm layer, without modifying tau2:

  • Prompted tool calls. Tools become a compact list in the system prompt; the model answers with one fenced JSON block per call; replies are converted back to native tool calls. Training data is rendered by the same code.
  • Context budget. A 512-token reply reserve; old results and replies are shortened before old turns are dropped; the dropped-turns note can restate the authenticated customer.
  • Guards and repair. Policy checks on each tool call before it runs (authenticate first, no made-up ids, explicit yes before a change, no repeated or endless lookups) and a deterministic repair of item ids sent to the product lookup.
  • Serving switches per system (tool_guards, state_reminders, condensed_policy, identity_note, agent_voice_check), recorded in every run and carried by a promotion, so the deployed system is served exactly as it was gated.

8. Remedies

Tool fix

Description patches: rules, then an LLM proposer constrained to description fields and validated against concrete ids; every patch in patches/ledger.jsonl with before and after hashes and a status history. Guards: llm/guards.py, ten rules from the retail policy plus a repair.

Weight fix

Three example sources: teacher replay of failed tasks under the student's own view, on-policy corrections at every turn a guard rejected (only the corrected turn is trained), and general function-calling examples disjoint from the gate's BFCL samples. A LoRA (r 16) trained with AgentTune's distill trainer and a masked, windowed loss.

9. The gate

Both systems run the same 20 held-out tasks three times in the same job. All eight checks must pass; missing evidence is a refusal. Thresholds are frozen in configs/gate.yaml; changes are logged with their reason in docs/evaluation.md.

CheckPasses when

valid_runs≥ 54 valid runs and ≥ 18 complete tasks per system
pass_1, pass_kthe candidate does not fall below the deployed system

non_targetno other failure label rises by more than 5 points

agenttune_gateAgentTune DeploymentGate approves on ≥ 54 paired runs

The gate job only serves and plays (vLLM with the adapter as a LoRA module); classification and the decision run in Cloud Run, where model tokens can be refreshed. Task splits are enforced in code: training reads only the train split, the gate only the held-out split, and the hidden split opens once for the final report.

11. Deployment

  • Image: infra/docker/Dockerfile, built only by Cloud Build on a push to a deploy branch; the job is pointed at the new digest, and shipwright run --launch waits for that before starting.
  • Jobs: shipwright-<owner> in asia-south1, 1 CPU, 2 GiB; the HF token as a Secret Manager reference; a dedicated runtime service account with least-privilege roles.
  • GPUs: HF Jobs launched as uv scripts with inline dependencies; flavors and timeouts per stage in the round config; a queued job is cancelled after 12 minutes and the next flavor tried.
  • Demo: the control room as a Docker Space (infra/space/), read-only, no secrets.

13. Security

  • No secret in code, images or logs: the HF token comes from Secret Manager in the cloud and from the environment locally; Vertex tokens come from the metadata server or gcloud, never Application Default Credentials.
  • The logger redacts hf_, ya29., Bearer and sk- values in every field.
  • Every gcloud call names its account config and project, so another identity on the same machine is never used.
  • Runtime and build service accounts are scoped to the bucket, secret and jobs they need.
  • Only allowed base models load (heal/systems.py).

14. Observability

  • Logs: one JSON object per line with run, task, turn, step, component, model, code sha and trace ids; every external call logs its target, latency, tokens, retries and status. In Cloud Run they land in Cloud Logging.
  • Traces: live OpenTelemetry spans (run, task, agent turn, model call, tool call) to Cloud Trace, and spans rebuilt from traces.jsonl with full text for any OTLP viewer.
  • Failure reports: every script writes errors.json (first error with the model's last input and output) and repro.json; scripts/why.py and scripts/rerun.py read them.
  • Control room: a round replayed step by step, with before and after conversations side by side.

17. Known limits

  • Small evaluation sets. 60 runs per system: two tasks flipping move pass^1 by 10 points. Gates select on the held-out tasks, and the hidden split, the independent check, has been used once.
  • The 8k window. Long lookup chains still overflow the student's context; guards and compaction reduce it, a larger window or fewer lookups per task would remove it.

18. Glossary

round
One remedy applied to the deployed system and gated; numbered across runs.
candidate
The system a round built: an adapter and serving switches, described by a system config.
deployed system
The last promoted candidate (configs/systems/current.yaml).
pass^1, pass^k
Share of runs solved; share of tasks solved in all k trials.
teacher replay
A stronger model solves the failed tasks under the student's view; its passing runs become training data.
on-policy correction
The teacher's reply at a turn where the current candidate went wrong, trained alone.
guard
A policy check on a tool call before it runs; the agent is asked again with the reason.
held-out, hidden
Test tasks for the gate, and test tasks opened once for the final report.
