Shipwright

A customer-support agent that finds its own mistakes, works out why it made them, fixes itself, and only ships the fix once it's measured to actually be better. Built for Lexsi Labs' AI Safety and Alignment Hackathon, Track 3 (self-healing agents).

1. What this is

Most AI agents fail quietly: something goes wrong mid-conversation, nobody notices, and the same mistake happens again tomorrow. This project is about closing that loop for a small, open-weight model instead of papering over it with a bigger one.

The agent is Tiny Aya Global, a 3.35-billion-parameter model from Cohere Labs, acting as a retail customer-support assistant that can look up orders, process refunds, and so on through a fixed set of tools. It runs real conversations against tau2-bench, a benchmark built for exactly this kind of tool-using agent, with a simulated customer on the other end and a strict grader checking whether the right thing actually happened in the system (not just whether the reply sounded right).

When the agent gets something wrong, the system doesn't just log it and move on. It works out why the failure happened, and that diagnosis decides what happens next: if the tool's own description misled the model, the fix is a one-line edit to the tool, verified and applied in minutes, no retraining. If the model itself reasoned badly, the fix is a small amount of further training, and - critically - that retrained version is only allowed to replace the old one if it's measured to be strictly better on tasks it's never trained on. A gate that can say no is the whole point: a system that always approves its own updates isn't really self-healing, it's just retraining on a schedule.

01

Run

Tiny Aya Global + LoRA plays the agent side of a tau2-bench task. The simulated customer and the grading are also an LLM (gpt-oss-120b), kept separate from the teacher model.

02

Log

Every turn's full raw model output is kept, not just the parsed tool call - otherwise a "the model reasoned its way to the wrong conclusion" failure is unclassifiable after the fact. OTel spans are built from the same trace for anyone who wants a standard trace viewer.

traces.jsonl · otel_spans.jsonl
03

Detect

A run is a failure if the task reward says so, or if AgentTune's own rule-based detector flags it independently (a tool call erroring, a loop of repeated steps). Both signals are kept, not just one.

AgentTune FailureDetector
04

Classify

Cheap, deterministic rules run first (did the model invent an id that only appears as an example in a tool's own description? did it repeat a call it already knows failed?). Only a failure no rule explains goes to AgentTune's real classifier, a model call.

rule labels · AgentTune FailureClassifier
05

Route

The classified root cause sorts into one of three branches, below. This mapping is our own addition - neither AgentTune nor AuditKIT has an opinion on which root causes are tool problems versus model problems.

Tool fault

The tool's own description misled the model: an ambiguous field, an example value the model copied as if it were real, a schema with no argument check.

Fix: edit the tool spec. No training. The edit itself is generated automatically, not hand-written, and cheaply first: a deterministic regex rewrites concrete example ids into placeholders in under a millisecond, no model call at all - and on its own, that rule produced every one of round 1's 35 patches. An LLM only steps in as the fallback, for whatever semantic ambiguity the regex can't catch, bound to a constrained prompt (no renaming fields, no concrete ids, keep it short) and the actual failure text. Every proposal is validated automatically before it's even added to the ledger. The one human step is deciding which proposed patches to apply - not writing them. Logged with a before/after snapshot and one-step rollback.
Model fault

The model itself reasoned or acted wrongly: picked the wrong tool, invented an id from nothing, looped, broke policy, hallucinated an answer.

Fix: a small amount of further training (LoRA), from one of two data sources - see below. Never ships without passing the gate.
Environment fault

Something outside the model's control: a timeout, an API error, the simulated customer itself making a mistake.

Fix: retry or skip. Never used as training data - training a model to compensate for a flaky environment teaches it the wrong lesson.

Two gates, by design, not by accident

The tool-fault and model-fault branches both generate their fix automatically, with no human writing a patch or a training example by hand. Where they deliberately differ is who signs off before that fix goes live - and the reason is the same reason in both directions: match the approval to how reversible the fix is before it ships.

Tool patch gate

Automated generation (regex, LLM fallback) → human approval.

Editing a tool's description changes the environment every agent sees, for every run, the moment it's applied - there's no sandbox to test it in first. A person decides which proposed patches go live; nothing else stands between a proposal and production.

approver: a person, every time

Model weight gate

Automated generation (teacher replay, Agent-R) → automated approval.

A new LoRA adapter doesn't touch anything until it's promoted: it can be loaded side by side with the one actually serving, scored on the same held-out tasks, and compared before it ever replaces anything. That side-by-side measurement is the eight checks below - nobody has to eyeball a diff and guess.

approver: the eight-check gate

Put another way: the tool gate is strict because it can't be sandboxed cheaply - the moment you'd test it, you've already shipped it. The model gate can afford to be fully automated because sandboxing it first is exactly what AgentTune's DeploymentGate and AuditKIT's scores are for.

06

Curate

Model-fault examples from both sources (teacher replay and Agent-R) are deduplicated and written as training rows in Tiny Aya's own prompt format - the same format it sees at inference time, so training data and live prompts never silently diverge.

scripts/build_sft.py
07

Train

A LoRA adapter (about 30M trainable parameters, <1% of the model) trains on the curated set. The loss is masked to the parts actually worth learning from - never the bad steps a revision run is correcting away from.

AgentTune create_distill_trainer, TRL SFTTrainer
08

Gate

Eight independent checks, described in full under Evaluation you can trust. All eight have to pass. A missing number or too small a sample fails its check - the gate never approves by default.

AgentTune DeploymentGate + AuditKIT
09

Promote, or roll back

Pass: the new adapter is tagged and pushed, the tool patch stays. Fail: the old adapter keeps serving, the patch reverts. Either way, one row is appended to metrics.jsonl and the next round starts from whichever version is now live.

4. Walking through it in more depth

The flow above is the whole story for most readers. These are the exact mechanics for anyone who wants them.

Why rules run before any model call in Detect/Classify

A model-based classifier costs money and time on every single failure. Several of the most common real failures turn out to be fully deterministic to spot: an id argument that matches an example value quoted inside a tool's own parameter description is always a copy-paste mistake, never a legitimate id. Catching that with a string match costs nothing and never calls a model; it's also exactly the failure mode that showed up in 13 of 19 real failures in the first baseline run. Only a failure no rule explains falls through to AgentTune's real FailureClassifier, which does call a model.

Why the tool-crash signal alone doesn't decide tool-fault vs model-fault

A tool call erroring could mean two very different things: the model picked the wrong tool for the situation (a one-off model mistake), or the tool's own spec is ambiguous enough that it keeps tripping up different runs (a tool problem, fixable once). The router tells these apart by watching whether the same tool keeps erroring across multiple different trajectories in a round. A repeat offender across unrelated tasks is a spec problem; a single bad call in isolation is the model choosing badly.

Why environment-fault failures are never used as training data

If the simulated customer glitches, or an API call times out, that failure has nothing to do with whether the model reasoned well. Training on it would teach the model to react to noise as if it were signal - the opposite of what a self-healing loop is supposed to do.

5. Two ways to fix a mistake

A model-fault failure can be corrected from two different sources, run independently, feeding the same curated training set. They don't compete - a round can use either, both, or neither, depending on what failures actually showed up.

Source A

Teacher replay

An open-weight teacher model (DeepSeek V4.1 Flash, never Tiny Aya's own weights) replays the failed task from the first wrong step onward, and its corrected trajectory becomes a training example - "here's what a stronger model would have done differently from this exact point."

Simple, cheap, and effective for failures where a clearly better action exists at the point things went wrong.

Source B

Agent-R (arXiv 2501.11425)

Instead of asking a different model what it would have done, this searches the student's own attempts at a task with Monte Carlo Tree Search, finds a successful branch and a failed one that share a path, has the model critique its own failed branch to find exactly where it went wrong, and splices in a short "wait, that's not right" revision thought plus the successful continuation.

The lesson is "notice your own mistake and recover," not "imitate someone else" - a second, complementary signal next to the teacher's.

Both sources write into the same training format: the bad steps are masked out of the loss (never trained on directly, only replaced), and only the corrective continuation counts as a target. train_lora.py asserts this mask survives intact through every step of data preparation - a silent masking bug would mean quietly training the model to repeat its own mistakes.

A real mistake, caught and reversed the same day

The teacher and judge roles were briefly set to a closed model (Claude) before anyone wrote any training code. That was wrong, and not a minor detail: the terms of service for Anthropic's, OpenAI's and Google's closed APIs all forbid using their output to train other models - and "the teacher model generates corrective examples that get trained into the student" is exactly that pattern, not a technicality around it. It was caught and reversed before any real call was made, by checking the license question before picking a model for a role that touches training data, not after. The fix: open-weight models only (DeepSeek V4.1 Flash, gpt-oss-120b), served through Vertex AI rather than through OpenAI's or Anthropic's own APIs, so no closed-model terms apply at any point in the pipeline. This is written down as a hard rule now, not a one-time correction - see the glossary entry for why this matters beyond just this project.

7. Evaluation you can trust

Three frozen splits, by exact task id

tau2-bench retail splits into a 74-task train pool and a 40-task test pool. The 40 test tasks are shuffled once (a fixed random seed) and cut into two fixed lists of exact task ids - not just a count - written into configs/splits.yaml so a benchmark update can never silently shift which tasks mean what:

train · 74 tasks · the loop learns from these held-out · 20 tasks · the gate scores on these hidden · 20 tasks · opened once, for the final report

A runtime guard refuses to run on the held-out/hidden split at all unless the exact task ids are named, and refuses the hidden ids specifically unless a flag explicitly opens them. The rule "never train on held-out or hidden tasks" is enforced by code, not just written down as a convention someone could forget.

The gate: eight checks, all required

A candidate is promoted only if every one of these passes. Any missing number, or too small a sample, fails its check - approving by default is not an option anywhere in this list.

#CheckWhat it guards against
1ComparableBoth systems ran the same held-out split, same task ids, same number of trials.
2Valid runsEnough non-infrastructure-error runs exist to trust the numbers at all.
3pass1The candidate's single-attempt success rate didn't drop.
4passkIts reliability across repeated attempts didn't drop.
5Target labelThe specific failure this round targeted actually dropped, and by a real margin - a tie is treated as no measured improvement.
6Non-target labelsFixing one thing didn't make a different kind of failure worse.
7BFCL v3General tool-calling ability (an external benchmark, not our own tasks) didn't regress.
8AgentTune's own gateAgentTune's DeploymentGate itself approves - run with an explicit minimum-sample floor, since its own default would otherwise approve on too little data.

Honest about sample size

20 held-out tasks is not a lot of tasks. A result like "20 of 20 passed" is a much weaker claim than it sounds - it's consistent with a true success rate anywhere from roughly 89% to 100%, not a guarantee of 100%. Every pass-rate number this project reports comes with a 95% confidence interval (the Wilson score interval, which holds up at small sample sizes where a naive calculation doesn't) alongside the raw percentage, specifically so a small-sample result never gets overstated as more precise than it is.

8. Library integration map

The hackathon's rule is that AgentTune and AuditKIT have to be the real engine, not a fallback dressed up to look like one. This table is the receipt: exactly which call does which job.

Detectagenttune.decide.closed_loop.failure_detector.FailureDetector Scans the audit log for loop-collapse and tool-crash patterns. Combined with tau2's own pass/fail, not used alone.
ClassifyShipwrightFailureClassifier, a real subclass of AgentTune's FailureClassifier Subclassed specifically to feed the full raw-text trace instead of the default's 2000-character truncation, which was cutting off exactly the reasoning text a wrong-reasoning failure needs.

CuratorKIT (the third, optional Track 3 library) is not currently used: its exporters have no tool-call schema at all, so using it would mean flattening every trajectory to plain text and reconstructing it afterward. A decision on whether that's worth doing is still open with the hackathon organizers; the pipeline works correctly without it either way.

9. Seeing what happened

Every script run writes structured logs (one JSON line per event, searchable by run id), a small reproducibility file recording exactly what was run and on what code version, and OpenTelemetry spans - both live, while a script runs, and exported afterward from the saved trace. The two directions round-trip: spans built from a trace convert back to the same trace losslessly, checked automatically on every commit.

When something breaks, scripts/why.py <run id> prints what failed, exactly where (which step, which task, which turn), the error and the model's last input and output, with direct links to the logs and the trace. scripts/rerun.py prints (or runs) the exact command to reproduce just that one failing task.

11. Watching the loop: control-room

A before/after comparison - one input, two model outputs side by side - is the natural demo for a team that trained one model once. It's the wrong demo here, because it hides the one thing that makes a self-healing system worth building at all: that it's a loop, with a gate in the middle that's allowed to say no. control-room is built instead to show exactly that - a read-only replay of a real round's actual artifacts, step by step, including a genuine gate rejection when the numbers don't support promotion. It never calls a model, a trainer, or the gate itself; it only reads what the real pipeline already wrote.

Status: runs locally today (streamlit run src/shipwright/control_room/app.py). A public Hugging Face Space is built and ready to deploy (infra/space/) but currently blocked on a platform requirement: HF now requires a PRO subscription to host any live-server Space (Docker or Gradio), not just a private one.

14. Glossary

AgentTune
Lexsi Labs' library for the actual self-healing mechanics: detecting failures, classifying why they happened, deciding when to retrain, and gating redeployment. The required engine for this track, not an optional helper.
AuditKIT
Lexsi Labs' evaluation library: scores a run's reliability across repeated attempts and compares it against an external tool-calling benchmark (BFCL). Produces the numbers the gate reads; has no gate of its own.
LoRA
Low-Rank Adaptation: a way to fine-tune a model by training a small add-on (here, about 30 million parameters) instead of all 3.35 billion, far cheaper and faster, and easy to swap out if it turns out worse.
tau2-bench
A benchmark for tool-using customer-support agents: real multi-turn conversations, a simulated customer, and a grader that checks the actual end state of the system, not just the words in the reply.
MCTS (Monte Carlo Tree Search)
A search method that tries many possible continuations of a situation and keeps track of which ones worked out, used here to find both a failed and a successful attempt at the same task that share a common starting point.
pass1 / passk
Pass1 is the success rate on a single attempt; passk is whether every one of k repeated attempts succeeds - a stricter measure of reliability, not just luck on one try.
Wilson score interval
A way of stating a success rate with honesty about sample size: "20 of 20 passed" becomes "consistent with a true rate of 89% to 100%," which is a more accurate claim than a bare percentage from a small sample.
BFCL
The Berkeley Function-Calling Leaderboard, an external, independent benchmark for tool-calling ability - used here purely as a regression check, so a fix for one problem can't be quietly making general tool use worse.
Closed-model training restriction
The terms of service of closed-API models (Claude, GPT, Gemini) forbid using their output to train other models. A teacher model that generates corrective training examples is doing exactly that, which is why this project uses only open-weight models in any role that touches training data.
