2. Route by failure type

Tool fault: patch the tool

  • Unclear tool description, loose schema, missing argument check.
  • Fix: edit the tool spec or add validation. No training.
  • Every patch goes in a ledger with a before/after snapshot, so the gate can roll it back.
  • Cheapest fix, so it runs first. Failures that remain go right.

Model fault: retrain

  • Wrong tool, bad argument format, wrong order, loop, policy break, invented answer.
  • Teacher (Claude / GPT) replays the task from the first wrong step and writes a fixed run.
  • Keep only fixed runs that pass the oracle. Drop the rest.
  • Curate: dedupe, balance by label, mix in old passing runs (replay).
  • AgentTune create_distill_trainer trains a new LoRA.

Environment fault: no fix

  • Timeout, API error, missing data, user-simulator mistake.
  • Retry or skip. Never train on it.
  • Experiment: show that training on these runs lowers pass^k.

3. Gate before redeploy

AuditKIT compares candidate vs current

  • Held-out task set, never used for training.
  • Ship only if: the targeted failure label drops AND pass^k does not drop AND BFCL v3 stays within the margin.
  • No default approve. Too few test runs means reject.
  • A planted bad model in round 2 must be rejected. That proves the gate works.

On pass / on fail

  • Pass: push adapter to HF Hub with a round tag, promote it, keep the tool patch.
  • Fail: keep the old adapter, roll back the tool patch, log why.
  • Each round writes one row to metrics.jsonl.
Loop: the promoted model starts round N+1 at step 01. Target: 3 or more rounds with numbers.

What we add

  • 3-way router: tool fix, weight fix, no fix.
  • Tool patch ledger with rollback (idea from Hermes agent, MIT).
  • AuditKIT gate with pass^k and BFCL, no default approve.
  • Real support domain, measured rounds, the tool-vs-weight comparison.
